## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
## Why

Exposes the magic-link flow over HTTP so the frontend can drive it. Two endpoints: request a link, and verify a clicked link (which mints a session). **Additive** — the existing password login (`POST /user-sessions`) stays in place and working; it is removed in the final task of this milestone, only after the frontend has cut over.

## Builds on

TASK-0018 provides the domain layer: issue-token (returns plaintext token + stores sha256 hash, 10-min single-use, supersedes prior), verify-token (constant-time lookup → resolved email, marks used), the `ALLOWED_EMAILS` allowlist gate, and the magic-link email template. This task only wires those into FastAPI routes + the email send.

## Current system context (for an implementer new to the repo)

- Routers live in `apps/backend/src/app/routers/`; see `user_sessions.py` (login/logout) and `users.py` (signup) for the existing patterns, including how `create_session(...)` is called and how the `sessionid` cookie is set (`settings.SESSION_COOKIE_NAME`, httponly, secure, samesite). **Set the cookie on verify exactly the same way the current login does.**
- The `EmailClient` is injected via the `email_client` dependency (`apps/backend/src/app/dependencies.py`); use `ConsoleEmailClient` assertions in tests (dev/test sink).
- Signup today is `POST /users` (`createUser`), which creates the user, starts a session, and best-effort sends `send_welcome_email`.
- Endpoints get OpenAPI `operation_id`s; the frontend client is generated by orval from the backend schema — regenerate it as part of this task.

## Decisions to make and document in the PR

- **Sign-up semantics:** recommended — verifying a valid link for an allow-listed but not-yet-existing email **auto-creates** the user (the allowlist *is* the gate), then sends the existing welcome email on first creation. Login and sign-up thus converge on one email-only flow. Document whatever you choose.
- **Enumeration safety:** `request-link` must return an identical response whether or not the email exists / is allow-listed ("if your email is allowed, we've sent a link"). Never reveal membership.
